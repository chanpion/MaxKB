## 新前端登录页 `get(...).then is not a function` 修复

**现象**：登录页 `fetchRsa` 调用 `get('/system/profile')` 报 `get(...).then is not a function`。

**根因（变量遮蔽）**：`store/user.ts` 用 zustand 的 `create<UserStore>((set, get) => ...)`，**第二个参数就叫 `get`**（zustand 的 store getter）。新加的 `import {get} from '@/lib/request'` 在 store 闭包内被这个局部 `get` 遮蔽，于是 `get(...)` 实际调用的是 zustand 的 `get`（返回 store 状态对象，非 Promise）→ `.then` 报错。

**修复**：把 request 的 `get` 起别名 `httpGet` 导入，并在 `fetchRsa` 中使用 `httpGet('/system/profile')`。lint 0 错误。

**经验（重构线通用坑）**：在 zustand store 工厂闭包里，`set/get` 是 zustand 注入的，不要再用同名导入 axios 请求方法（`get/post/...`）。需要用时务必别名（如 `httpGet`/`httpPost`）。

## 登录 `Invalid username or password` 诊断

**现象**：前端（Next.js 重构前端，走 FastAPI 8081 后端）登录 admin 报 `{"detail":"Invalid username or password"}`。

**诊断方式**：直连 `backend/.env` 的 PG（`postgresql://postgres:pgvector123@127.0.0.1:5432/maxkb`），查 `user` 表 admin 行，并用 `backend/app/core/password.verify_password` 实测。

**结论**：账号存在、`is_active=True`，但存储的密码哈希是 **Django 默认** `pbkdf2_sha256$1000000$...`，实际密码为 `MaxKB@123..`（verify 返回 True），用户以为的 `Kb@123456` 验证为 False。即登录拒绝是**正确行为**——密码认知错误。

**处理**：用与 Django 完全一致的 `pbkdf2_sha256$1000000$<salt>$<b64>` 算法（salt=12 位字母数字，dklen=32）重算哈希并 `UPDATE "user" SET password=... WHERE username='admin'`，使 `Kb@123456` 可登录。

**注意**：新后端与 Django 共用同一 PG/Redis；`user` 表由 Django 建表与初始化（默认 admin 密码 `MaxKB@123..`）。改密码请用 Django 兼容哈希，否则 `verify_password` 不认。

## 知识库子文件夹显示为同级（tree 不嵌套）
**现象**：在知识库页面新建子文件夹后，页面上它和父文件夹显示在同一级。

**根因**：前端 `FolderVirtualizedTree.load()` 依赖后端 `GET /workspace/{ws}/{KNOWLEDGE}/folder` 返回**嵌套树**（每个节点带 `children` 数组）。但 `backend/app/api/knowledge.py` 的 `list_knowledge_folders` 返回的是**扁平列表**（只有 `id/name/desc/parent_id`），无 `children` → 前端无法嵌套。库内 `parent_id` 本身是对的（如 `test`.parent_id=通用uuid），只是后端没组装成树。

**修复**：在 `list_knowledge_folders` 中查出全部文件夹后，按 `parent_id` 构建嵌套树并挂 `children`；根节点 = `parent_id IS NULL` 或 `parent_id` 指向不存在的文件夹。排序由 `lft` 改为 `create_time`（新建文件夹 `lft=0` 会乱序）。

**注**：MPTT 列（lft/rght/tree_id/level）对新建文件夹均为 0、未维护；但前端展示只依赖 `parent_id` 树，本次修复已解决显示问题。若以后有别的功能依赖 MPTT 区间查询，需单独处理插入时的 lft/rght 计算。

## 知识库文件夹「资源授权」404 修复
**现象**：Vue `ui/`（端口 3001，代理到新后端 8081）打开知识库文件夹的资源授权抽屉，请求 `/workspace/default/resource_user_permission/resource/{folderId}/resource/KNOWLEDGE_FOLDER/1/20` 返回 404。

**根因**：新 FastAPI 后端完全没有 `resource_user_permission` 这套路由（Django 端在 `apps/system_manage/views/user_resource_permission.py` 的 `WorkspaceResourceUserPermissionView`）。

**修复**：
1. `backend/app/middleware/path_rewrite.py` 的 `LEGACY_ALIASES` 增加 `(r"^/api/resource_user_permission/(.+)$", r"/api/system/resource_user_permission/\1")` —— 因为 `/workspace/{ws}/` 段会被 `WS_RE` 先剥掉，最终落到 `/api/system/...`。
2. `backend/app/api/system.py` 新增两个路由（对齐 Django 行为）：
   - `GET /resource_user_permission/resource/{target}/resource/{resource}/{current_page}/{page_size}`：列出用户及其在该资源上的有效权限，`resource` 含 `_FOLDER` 后缀需 `replace('_FOLDER','')` 得到 `auth_target_type`；返回 `{"records":[{id,nick_name,username,permission}],"total":N}`，由 legacy 响应中间件包成 `{code,data:{records,total},message}`（前端 `res.data.records/total`）。
   - `PUT /resource_user_permission/resource/{target}/resource/{resource}`：body 为 `[{user_id,permission,include_children?,folder_ids?}]`，先删后建 `workspace_user_resource_permission`，`permission_map` 同 Django（ROLE/MANAGE/VIEW/NOT_AUTH → auth_type+permission_list）。
   - 权限推导 `_derive_permission` 对齐 SQL：`ROLE`(ROLE 类型且含 ROLE) / `MANAGE` / `VIEW` / 否则 `NOT_AUTH`。

**验证**：`_rewrite` 单测通过，路由已注册，无 lint 错误。重启后端 8081 后即可。

## 前端首页 404（/frontend/home）

**现象**：访问 `http://localhost:3000/frontend/home` 报 404。

**根因**：`frontend/next.config.mjs` 设 `basePath: ''`，应用挂载在站点根路径（注释明确"不再使用 /frontend 前缀"）。实际路由无 `/frontend` 前缀，首页是 `/home`，根路径 `/` 按登录态重定向到 `/home` 或 `/login`。

**结论**：用户确认直接用 `/home` 访问，无需改为 `/frontend` 部署。若将来要部署到 `/frontend` 子路径，需改 `basePath: '/frontend'` 并同步 `middleware.ts` 的 matcher 与 rewrites。

## 首页菜单误跳 `/frontend/home`（真实 bug，已修）

**现象**：点击首页菜单跳到 `http://localhost:3000/frontend/home` 报 404（之前以为是用户用错地址，实为代码 bug）。

**根因**：`frontend/src/lib/constants.ts` 把 `HOME_PATH='/frontend/home'`、`LOGIN_PATH='/frontend/login'` 写死了 `/frontend` 前缀，但 `next.config.mjs` 的 `basePath` 是空串。next-intl 的 `useRouter().push()` 不会叠加空前缀，于是写死的前缀原样进 URL → 404。TopMenu 用 `router.push(HOME_PATH)` 触发。

**修复**：
- `constants.ts`：`HOME_PATH='/home'`、`LOGIN_PATH='/login'`（去掉 `/frontend`）。
- `lib/request/index.ts`：401 跳转 `window.location.href='/frontend/login'` → `'/login'`。
- 其余导航（/application、/knowledge 等）本就用干净路径，无需改。middleware 内 `LOGIN_PATH/HOME_PATH` 已是 `/login`/`/home`，与常量一致。

**教训**：`basePath` 为空时，应用内路径常量**不能**带 `/frontend` 等前缀；如需按子路径部署，必须 `basePath` + 常量前缀 + middleware matcher/rewrites 三处同步。

## 工具页报"范围:该字段不能为 null"

**现象**：点工具菜单进 `/tool` 页面，前端弹错"范围:该字段不能为 null"。

**根因**：`frontend/src/lib/api/tool/tool.ts` 的 `getToolList` 调 `GET /workspace/{ws}/tool/tool_list`，但没传 `scope`。该 URL 在 `apps/tools/urls.py:17` 映射到 `ToolView.Query`，其 `get`（views/tool.py:326）写 `'scope': request.query_params.get('scope')`（**无默认值**），交给 `ToolSerializer.Query`（serializers/tool.py:345 `scope = CharField(required=True, label=_("scope"))`），`get_tools()` 开头即 `is_valid(raise_exception=True)` → scope=None 校验失败 → DRF 返回中文校验错误 `范围:该字段不能为 null`。
对比 `ToolView.get`（line 86）对 scope 有默认值 `ToolScope.WORKSPACE`，两处不一致。

**修复**：新前端 `getToolList` 补传 `scope: 'WORKSPACE'`，与旧版 Vue 前端 `getAllToolList` 行为一致（见 `ui/src/views/application/ApplicationSetting.vue:1322` 等）。改动：`get(`${prefix.value}/tool_list`, {scope:'WORKSPACE', ...param})`。

**经验**：新前端调 Django 接口前，应比对旧版 Vue 前端同接口的传参；Django 侧部分接口对 query 参数必填且无默认值（如 scope），缺参会直接 400 校验错误。前端 `.env.local` 的 `API_TARGET=http://localhost:8080/` 指向 Django 后端（非 8081 FastAPI）。

## 知识库 split 接口返回格式错位（已修）

**现象**：Vue `ui/`（代理到新后端 8081）在知识库页面上传文档、点"分段预览"时，split 接口返回 `{code,data,message}` 中 `data` 结构异常：每个**段落**被拆成独立 item（`name:"架构设计.md-1"`、`content:[单个段落]`），导致前端预览渲染错位。

**根因**：`backend/app/api/knowledge.py` 的 `split_document` 错误地做"按 `\n\n` 切分 → 每个段落生成一个 `{name:文件名-N, content:[该段]}`"。而老后端 `DocumentView.Split` + `split_model.SplitModel.parse` 的契约是：**每个文件一个 item**，结构为 `{name:文件名, content:[{title,content}...], source_file_id}`，且切分走 markdown 标题/空行正则 + 长度智能分段。

**修复**：重写 `split_document`：
- 入参改为 `files: list[UploadFile]`（支持多文件，对齐 Django `request.FILES.getlist("file")`）。
- 复用已有的 `backend/app/rag/splitter.py`（`SplitModel`/`get_split_model`，即老 `split_model.py` 的移植版），对**整个文件**产出完整 `{title,content}` 段落列表。
- 每个文件返回一个 item：`{name: file.filename, content: paragraphs, source_file_id: uuid4()}`。
- 可选 `patterns`（JSON 正则数组）走自定义切分，否则按 `.md`/default 模式表回退，与老后端一致。
- `limit` 默认值改回 4096（与老 `get_split_model` 一致），`with_filter` 默认 True。
- 删掉了原 `session` 依赖（未使用）。

**链路校验**：老 `ui` 的 `SetRules.vue` 读 `res.data` 每个 item 的 `name`/`content`（每项带 `title`），`UploadDocument.vue` 再映射为 `{name, paragraphs: item.content, source_file_id}` 提交到 `batch_create`；新后端 `batch_create_documents` 正好读 `paragraphs`。三者现已对齐。`{code,data,message}` 由全局响应中间件包裹，无需改动。

**注意**：`source_file_id` 当前为新生成的 uuid（文件未真正落库）。新后端 `batch_create_documents` 不消费该字段，故无副作用；若日后要在新后端还原"源文件关联/PDF 预览"，需把文件存入 `File` 表并返回真实 id。
